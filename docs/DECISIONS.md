# Decisions made during implementation

What was agreed with the user during design was followed as is. Below are the choices made while implementing. To change one, refer to it by number.

## Storage and layout

1. **State is a single JSON file, not SQLite.**
   - Tasks, Workers, decisions and chat live in `<home>/data/state.json`, written atomically and batched every 300 ms.
   - Worker conversations go to `<home>/data/workers/W-xx.jsonl`.
   - Why: without native modules, Windows and macOS packaging stays simple. A personal tool has little data.
2. **Memory search scans the markdown for word matches instead of SQLite FTS.**
   - As agreed, markdown plus git is the source of truth. Add FTS if it slows down past a few hundred files.
3. **One worktree per Worker per repository** (`<home>/worktrees/<repo>/<W-id>`).
   - For each task the Worker creates a new `agent/t-xxxx` branch inside that worktree.
   - Why: when the same Worker continues, the session's folder must not change (resume is tied to the folder path).
4. **When a PR is merged or closed** the local and remote branches are deleted and the worktree goes back to the default branch.
   - The worktree folder itself is removed when the Worker is archived.
   - This is the only difference from the agreed plan ("delete the worktree on merge"): a Worker that keeps its context needs its folder to take the next task.
5. **Output of non-code tasks** goes to `<home>/workspaces/<W-id>/<T-id>/`.
6. **Repository registration accepts a git URL, `org/name` (turned into a company GitHub URL), or the path of a folder already cloned.**

## Agents

7. **Dispatcher tools.**
   - Read-only tools only: Read, Glob, Grep, WebSearch, WebFetch.
   - Plus the IDE task-board MCP tools: `list_repos`, `register_repo`, `list_workers`, `create_task`, `send_to_worker`, `ask_worker`, `read_worker`, `stop_worker`, `cancel_task`, `clear_queue`, `request_decision`, `remember`, `recall`, `task_detail`.
   - It cannot edit code.
8. **The MCP server is named `board`.** Claude Code reserves `ide` for IDE integration and filters its tools. This actually happened.
9. **Effort.** Dispatcher medium, Workers high, the answer-on-your-behalf check low.
10. **The Dispatcher starts a new session each day.**
    - Its system prompt carries a memory digest and the repository list.
    - Worker news does not wake the Dispatcher; it is prefixed to the next user message. This avoids extra turns and cost. Now news worth a turn starts one (decision 87); the rest still waits for the next message.
11. **Worker result format.** The final message starts with `RESULT:`, `PR:` and `FILE:` lines that the app parses. Result cards take their summary, PR link and file links from these.
12. **A follow-up (from the user, the Dispatcher, or a correction) on a task finished less than 3 days ago** reopens that task, and its result card says "Applied the follow-up".
13. **On restart** running Workers reopen their sessions and get a "continue where you left off" message. Pending questions and permission requests are withdrawn; Workers ask again as they continue.

## Questions, permissions, answering on the user's behalf

14. **The app intercepts Workers' AskUserQuestion.**
    - First the Dispatcher model checks memory and answers only with clear support (structured output).
    - Without support, the question goes to the decision inbox and the Worker waits.
    - It never answers questions that are hard to undo: cost, security, deleting data, making something public.
15. **Permissions.** Auto mode is used; only what auto mode cannot decide goes to the decision inbox.
16. **Always ask, regardless of auto mode** (PreToolUse hook):
    - force push
    - direct push to main, master, develop, release/*
    - DROP/TRUNCATE, DELETE without WHERE
    - production database clients
    - kubectl, terraform, helm changes
    - `gh pr merge`, deleting a repository or release
    - `rm -rf` of the root or home folder
    - (Editing files outside the Worker folder was on this list until decision 58.)
17. **Answers given in the decision inbox** are kept in memory under `decisions/YYYY-MM.md`. Finished tasks go to `tasks/YYYY-MM.md`.
18. **Corrections.**
    - "Just this once" sends only a `[Correction]` message to that Worker.
    - "Fix the preference" also rewrites the line in `preferences.md` the answer was based on.

## Accounts and usage

19. **Two kinds of account.**
    - A token from `claude setup-token`, encrypted with the OS secure store.
    - This PC's Claude Code login as is. Only one can be registered.
20. **Assignment.**
    - Pick the account whose larger of 5-hour and 7-day usage is lowest.
    - Within 5 points, pick the one assigned longest ago.
    - Accounts above 80% get no new sessions.
21. **Hitting a limit.**
    - A limit error mid-task resumes the same session with another account's token.
    - When every account is above 80%, new work is queued and retried every 2 minutes.
22. **Usage comes from three places.**
    - Token accounts: Claude Code's usage endpoint every 5 minutes.
    - Rate-limit events from every session.
    - The session usage API after each turn (at most once a minute). This also fills tokens without endpoint access and the login account.
23. **Child process environment.** Started from a Claude Code terminal, the app inherits variables such as `CLAUDECODE` and `CLAUDE_CODE_*`, which confuse child sessions. They are stripped.

## Compaction, archiving, notifications, PRs

24. **Compaction.** When a turn ends above 250K context, `/compact` is sent. That turn is hidden. Now at 200K, with Claude Code compacting mid-turn too (decision 79).
25. **Auto-archive.**
    - Workers idle for the configured period (default 7 days) are archived. Workers with an open PR or a task waiting for a merge are not.
    - If the Dispatcher gives an archived Worker new work, it is restored automatically.
26. **Notifications.**
    - Decisions: the app's own sound, an OS notification, taskbar flash on Windows (Dock bounce on macOS), and a blinking sidebar.
    - Finished tasks: a silent notification, only while the window is in the background.
27. **PR checks.**
    - Every 3 minutes, `gh` checks open PRs.
    - New conversation, review or inline comments (bots excluded) are handed to the Worker that opened the PR to address and push.
28. **The CLAUDE.md PR** is created only from the button shown when `repos/<repo>.md` is open in the Memory view. The Worker that has been working on that repository takes it if there is one.

## UI

29. **Windows window.** The title bar is hidden and the OS window buttons overlay the top right. On macOS the traffic lights sit above the sidebar.
30. **Fonts.** System fonts only, so it looks the same offline.
31. **Shortcuts.**

    | Key | Action |
    |---|---|
    | ⌘/Ctrl+1–4 | Switch view |
    | ⌘/Ctrl+, | Settings |
    | ⌘/Ctrl+Z | Undo clearing a list |
    | Enter | Send |
    | Shift+Enter | New line |

    While the Dispatcher is working and the input is empty, the send button becomes a stop button.
32. **No "add repository" button.** During the mock review we agreed that adding happens through the chat. The Repositories view can edit descriptions and unregister.
33. **Model IDs are editable in Settings.** Defaults: Dispatcher Sonnet 5.5, Worker Opus 5.5, design work Fable 5.2.

## Packaging

34. **NSIS installer on Windows, dmg on macOS.**
    - The SDK's Claude binary is unpacked outside the asar.
    - No code signing. It is a personal tool, so the OS warns once on first run.
35. **`OMA_DATA_DIR`** puts settings and data in another folder. Meant for testing; also works as a second profile.

## Round 3 (0.2.0)

36. **Usage endpoint 429 is not an account limit.** It is the usage endpoint's own request limit (Claude Code on the same PC calls it too). The app keeps the last known values, shows no error, and waits for Retry-After or 15 minutes before asking again. The 7-day number appears only when the endpoint or the session usage API reports it; rate-limit events during work only carry the 5-hour window. Unknown values show as "–" in both the toolbar and Settings, with a tooltip saying why.
37. **Language.** English is the default; Korean can be chosen in Settings → General. All UI text lives in `src/shared/i18n.ts`. Agent prompts are written in English and tell agents to write to the user in the chosen language. Chat lines already written stay in the language they were written in. Code, comments, docs and commit messages in this repository are in English.
38. **PR language for Workers.** Workers follow the language of the repository's recent PRs; without a clear convention they use the UI language.
39. **Settings layout.** Sections on the left (Accounts, General, Display, Notifications, Memory, Models), the chosen section on the right, one Save button for everything. Switching sections keeps unsaved values. Settings carry no explanatory paragraphs; labels and placeholders only.
40. **Accounts: at most 4, each marked Team or Enterprise.** The plan is a label the user picks; it does not change assignment. Accounts that report no usage window are scored as 0% and rely on rate-limit events, as before.
41. **Decision sound.** Built-in sounds are synthesized with Web Audio (chime, bell, ping), so no audio files ship with the app. A custom file (mp3, wav, ogg, m4a, aac, flac, up to 8 MB) can be chosen. OS notifications are silent so the sound plays only once. Windows needs an AppUserModelID for toast notifications, so the app sets `dev.ohmyagent.ide` (same as `build.appId`).
42. **Dropped files are passed as paths, not copied or uploaded.** The message gets an `[Attached files]` list of absolute paths. The Dispatcher puts those paths in the task prompt, and Workers may Read, Glob and Grep at or under them without a permission prompt. Other writes still follow the normal rules. Files dropped anywhere else in the window are ignored instead of opening in the window.
43. **Tasks that wait for a merge.** `create_task` takes `after_task_id`. Such a task is assigned right away (the Worker shows "After merge") but starts only when the PR monitor sees that PR merged. If the PR is closed without merging, the waiting task is cancelled and the chat says so; the Dispatcher hears it with the next message. A merge also posts a silent notification, marks the result card "merged", and is checked again whenever the window comes to the front (at most once a minute) in addition to every 3 minutes.
44. **Font and text size** (from PR #1) are set in Settings → Display and stored as `fontFamily` (empty = system font) and `fontSize` (10–20 px, default 13) in `settings.json`.
    - The chosen font applies to all UI text, with the system fonts appended as fallbacks. Code and logs keep the monospace font.
    - Text size scales every font size relative to 13 px (`--ui-font-size`, `--px`); window and panel widths stay the same.
    - Changes preview live in the settings sheet and revert if you close without saving.
45. **Effort.** Settings hold a default effort for the Dispatcher (medium) and for Workers (high). With "Effort per task" on (default), `create_task` takes an optional `effort` and the Dispatcher sets it only when a task clearly needs more or less than the default; the Worker session switches level live (`applyFlagSettings`) before each task. With it off, every task uses the Worker default.
46. **Custom controls instead of native ones.** Dropdowns are pop-up buttons with a popover list (keyboard: arrows, Enter, Escape). Number fields are steppers, volume is a custom slider. The font picker lists only fonts installed on this computer (read with `queryLocalFonts`), each shown in its own typeface; a typed name that is not installed gets an orange outline. Fonts that aren't installed used to fall back to the system font silently, which is why picking a suggested font seemed to change nothing.
47. **Settings is a full window, not a sheet** (from the approved mockup).
    - Top bar: back to the workspace on the left, the title fixed in the center, and "Unsaved changes", Revert and Save on the right. The title never moves when the label appears.
    - Save keeps the window open. Leaving with the back button or Escape drops unsaved changes.
    - The left list has a search box that keeps only the sections whose labels match, and the app version at the bottom. Its icons are plain line icons; the chosen one is blue.
    - Content is centered at 680 px in grouped rows.
48. **Segmented controls replace dropdowns** wherever the choices are few: plan, language, decision sound, models and effort. The play button matches the control's height. Model choices are fixed lists; a model ID set earlier that is not in the list stays as an extra choice. Only the font keeps a list (installed fonts).
49. **Accounts are cards** with initials, plan badge, login kind and 5h/7d meters (orange at 80% and above). The ⋯ menu has Rename, Refresh usage, Plan and Remove. Rename edits in place (Enter saves; Escape or a click elsewhere cancels). Remove asks in a small dialog. A click outside the menu closes it.
50. **Fonts with coarse Hangul at small sizes.** D2Coding's `gasp` table turns smoothing off at 9–16 ppem, but Chromium on Windows ignores `gasp`: a copy with `gasp` set to smooth renders pixel-for-pixel the same. So the app does not patch fonts. Coding fonts look rough as the UI font because of their design at 13 px.

## Round 4: ideas from other agent IDEs

The survey is in [RESEARCH-agent-ides.md](RESEARCH-agent-ides.md).

51. **Plan-first tasks.** `create_task` takes `plan_first`. The Dispatcher sets it when the user asks to see the approach first, or when a code change is large, risky or open to several designs. The Worker session runs in plan mode (read-only) until the plan is approved. Its `ExitPlanMode` call becomes a "Review the plan" card in the decision inbox. The plan starts with three one-sentence lines, `WHAT:` / `HOW:` / `OUTPUT:` (not `RESULT:`, which is the final-report line of decision 11), so the user can approve from the card alone: it shows them as What / How / Result, keeps the full plan (rendered as markdown) folded under Show details, and links to the Worker's conversation. A plan without the lines is sent back once, without asking the user, to add them; a second one without them is taken, and the card shows lines pulled from the plan's title and first sentences, marked auto-extracted. The sidebar row and the OS notification show the WHAT line. Approve switches the session to auto mode and the Worker builds. Typed feedback denies `ExitPlanMode` with that text, so the Worker revises and presents the plan again. Like other pending requests, an open plan card is withdrawn on restart; the Worker resumes in plan mode and presents it again.
52. **Changes tab in the Worker conversation** (repository Workers only). It lists files that differ between the worktree and its merge base with `origin/<default>`: committed and uncommitted changes, plus untracked files. Each file expands to its diff. The diff is read when the tab opens or Refresh is pressed, not on every state update. Patches are capped at about 600 KB in total so a huge change cannot freeze the window. Reading only: changes still go through the Worker.
53. **Setup command per repository.** Set in the Repositories view. It runs once in each new worktree, through PowerShell on Windows and the login shell elsewhere, with `ROOT_PATH` set to the main checkout (for example `cp $env:ROOT_PATH/.env .`). A failure is reported in the chat; the Worker still starts.
54. **Usage in the toolbar with 3 or 4 accounts.** One row per account no longer fits the 52 px toolbar, so from three accounts on they sit two per row and the "5h"/"7d" labels are dropped (the bars stay in that order). Hovering an account shows its name, both percentages and when they were read.
55. **Usage past its reset time is ignored.** A 5h or 7d value whose `resetsAt` has passed counts as unknown (0 for picking accounts, "–" on screen). Before this, an account stored above 80% stayed "limited" after the window reset. A PC-login account learns usage only from running sessions, and none start while every account looks limited, so the app could stay stuck.
56. **Composer.** No placeholder text. The box grows with its text up to half the window, then scrolls with the scrollbar hidden. The stop button had picked up the settings top bar's `.stop` layout and stretched into an ellipse; that bar's class is now `.stopbar`.
57. **UI polish pass.**
    - Selection prompts and "nothing here" states show a title only. The sidebar's "nothing in progress" is one quiet row instead of a large block. The first-run chat and empty Repositories views keep their one line of guidance, since adding a repository only works through the chat.
    - The settings account badge used the global `.pill` class and turned every status pill blue (idle Workers looked busy). It is now `.plan-badge`.
    - The Worker conversation subtitle shows repository · branch · model.
    - Long paths: the Repositories inspector shows the last three segments with the full path on hover; the IDE home field in Settings scrolls to the end.
    - A Worker's final report shows its `RESULT:` line as a bold summary with PR and file chips, instead of the raw `RESULT:`/`PR:`/`FILE:` lines.
58. **File edits are left to auto mode.** The always-ask list no longer includes edits outside the Worker folder. Claude Code itself writes outside the worktree all the time (auto-memory under `~/.claude/projects`, plan files under `~/.claude/plans`, its temp scratchpad), so the rule filled the decision inbox with harmless requests. Auto mode still asks through the inbox when it cannot decide. The always-ask list keeps only destructive or shared-state shell commands (decision 16).
59. **Dependency audit.** All direct dependencies were already at their latest versions; the 6 moderate warnings came from `minimatch` 9.x and 10.x inside electron-builder (GHSA-g3hv-75wg-m249). `npm audit fix --force` would downgrade electron-builder, so `package.json` overrides only those two ranges to `^11.0.9`. The 3.x and 5.x copies are outside the advisory and keep their older API. `npm audit` reports 0; the Windows installer builds and the packaged app starts. The macOS-only `@electron/universal` path is untested until the next dmg build.
60. **Compact or clear the Dispatcher by hand.** The context indicator next to the send button opens a menu: Compact conversation sends `/compact` to the current session (hidden turn; the chat notes the size before and after), and Start new conversation drops the session so the next message starts fresh. The chat on screen, Workers, tasks and memory stay. Both are disabled while the Dispatcher is working or has no context. Automatic compaction at 250K stays as before.
61. **Claude Code rules and memory reach every agent, like subagents.** Claude Code passes CLAUDE.md to its subagents and keys agent memory by role, not by run; the app does the same.
    - **Rules:** `~/.claude/CLAUDE.md` and `~/.claude/rules/*.md` (or under `CLAUDE_CONFIG_DIR`) are read and appended to the Dispatcher's and every Worker's system prompt (up to 20K characters), and given to the auto-answer check. The `user` settings source stays off, so `~/.claude/settings.json` (permissions, hooks, MCP) does not reach agent sessions.
    - **Auto-memory:** a Worker's `autoMemoryDirectory` is the Claude Code memory of its repository's main checkout (`~/.claude/projects/<checkout path>/memory`), so all Workers on a repository and the user's own Claude Code sessions there read and write one memory. Workers without a repository share the IDE home's, which is also the Dispatcher's. Workers are told to save only durable repository or preference facts there, never task progress. Verified with a live session: the folder's `MEMORY.md` index is loaded.
    - **recall tool:** Workers get `recall` (MCP server `oma`) over IDE memory plus their shared Claude Code memory. The Dispatcher's `recall` also searches the Claude Code memory of every registered repository and of the IDE home.
    - Repositories registered by URL live under `<home>/repos/<name>`, where the user has not run Claude Code, so their shared memory starts empty.
62. **Second UI pass on the main screen.**
    - Results list task outcomes only. Errors without a task (every account at its limit, Dispatcher errors) stay in the chat, where the same error repeated back to back shows once with a count.
    - Each result shows when it finished: the time today, the date before that, the full time on hover.
    - Agent summaries render `code` spans in result cards, the results list and Worker reports.
    - Multi-line chat events keep their icon at the first line; usage percentages keep a gap before the next label.
63. **Settings pass.**
    - **Add account** starts with the sign-in method (Token or This PC's login). The token field and the matching button show only for the chosen method; the method choice is hidden once a PC login is registered.
    - **Memory** has two groups. IDE memory: its folder (Open) and the remote. Claude Code: which rule files were found, a switch for passing user rules to agents (`claudeRules`), a switch for sharing the repository's Claude Code memory with Workers (`claudeMemory`; off turns Claude Code auto-memory off for Workers instead of one per worktree), and the Claude Code folder (Open). Changing either switch gives the Dispatcher a fresh session; Workers pick it up when their session starts.
    - The text preview in Display uses the chat window's background instead of black.
    - The company GitHub host keeps only the host name (scheme, path and case are dropped).
64. **App icon.** Stacked frosted glass windows with a prompt on a blue squircle, in the Liquid Glass style of macOS Tahoe / iOS 26: the windows blur what lies beneath them, carry a thin top-lit rim, and cast soft blue shadows. It stands for several agent sessions running at once. `scripts/make-icon.mjs` writes the SVGs into `build/` and `scripts/render-icon.cjs` renders them with Chromium (`npm run icon`):
    - `build/icon.png`, 1024 px on the macOS grid (824 px body with room for its shadow); electron-builder makes the `.icns` from it.
    - `build/icon.ico`, 16 to 256 px, with a larger body for Windows. Each size is rendered from the vector. At 32 px and below a simplified layout (two windows, heavier prompt, no fine shadows) keeps it legible in the taskbar.
65. **Liquid Glass UI.** The main window and Settings follow the macOS Tahoe look.
    - **Floating panels.** The sidebar, inspector and Settings navigation float as rounded glass panels, inset 8 px from the window edge. Each panel shows the blurred backdrop through it, has a soft sheen at the top, and carries a specular rim: light from the upper left catches the top and left edges, with a fainter glint opposite.
    - **Capsule controls.** The toolbar has no bar of its own: the view switcher and usage sit on it as glass capsules. Buttons and segmented controls are capsules too; the default button uses the accent gradient. Menus, dialogs and toasts are glass sheets over the content.
    - **Floating composer.** The message box floats over the end of the conversation as a glass capsule, so messages scroll under it. The conversation keeps room below its last message for the composer's current height, measured as it grows. If the view was at the end, it stays there.
    - **Window stays opaque.** The window does not use the OS material (Windows acrylic, macOS vibrancy); the app paints its own backdrop instead: neutral graphite (`#131316`), slightly lighter at the top. A blue and violet wash was tried first and dropped as too loud. The desktop showing through hurt legibility behind busy wallpapers, transparent Electron windows have resize artifacts on Windows, and neither could be checked on screen here.
    - On Windows and Linux the sidebar does not keep the empty band reserved for the macOS traffic lights. The traffic lights now sit inside the floating sidebar.
    - Text boxes in inspectors grow with their text instead of showing a resize grip.
    - With Reduce transparency (macOS) or transparency effects off (Windows), surfaces turn solid and nothing is blurred.
66. **Selection slides like Liquid Glass.** Every segmented control (the view switcher, the Worker conversation/changes tabs, the choices in Settings) has one glass pill under the chosen segment. Choosing another slides the pill there with a slight overshoot and stretches it along the way. A control that is new, shown again or resized places the pill without motion; with Reduce motion it never animates. The pill follows the selection however a control was updated, so re-rendered controls need no extra code.
67. **Settings save as they change.** No Save or Revert. Switches, segments, pickers and steppers save at once; typed text after a short pause or when the field loses focus. The IDE home folder saves only when its field loses focus or a folder is picked, then asks in an in-app dialog whether to restart now. The home folder is now read once per launch, so a new one really waits for the restart (before, part of the app switched to it right away). Changing it back to the folder in use asks nothing.
68. **Models come from the API.** Settings > Models lists every model the registered accounts can use, read from the Anthropic API's model list (`GET /v1/models`) with an account's token, newest first. New models appear without an app update. The list is kept in `models.json` in the app data folder: it is read again at startup when older than 6 hours, on opening Models when older than a minute, and by Refresh. If no token can read it (macOS keeps the PC login in the Keychain; a PC login token may have expired), the running Dispatcher session's list from Claude Code is used. Otherwise the last list stays. Each role (Dispatcher, Worker, design work) picks from the list in a dropdown that shows the name and the model ID; a configured model missing from the list stays selectable. Model names elsewhere come from the same list.
69. **Default home folder is `~/oh-my-agent-ide`.** New installs use it. Existing installs keep the folder already saved in their settings; changing it in Settings does not move data.
70. **UI fixes.** The account menu in Settings drew under the next card (each card was its own blur layer); settings cards no longer blur, which changes nothing visible on the plain backdrop. Labels in info tables (Repositories, Workers) size to the longest label up to 140 px and wrap past that, instead of a fixed 84 px column that "Default branch" overflowed.
71. **Dark window frame on Windows.** The UI is dark only, but Windows draws the window frame from the system theme. In light mode the outline was light, and on a monitor whose DPI differs from the primary one a 1px `#f3f3f3` strip showed on the left, right and bottom edges (Chromium leaves that strip to the system frame; it cannot be removed from the app). On Windows the app now sets `nativeTheme.themeSource = 'dark'`, so the frame is dark (the strip turns `#202020`, next to the `#131316` canvas). macOS and Linux keep following the system theme; nothing there changes.
72. **Route at any usage; retry when a limit resets.** The 80% rule is gone. A new session takes the account with the lowest usage, however high. An account is skipped only after a usage limit actually rejects it, and only until that limit resets: the rejection's own reset time, else the latest reset among full windows, else 30 minutes. A failing session moves to another account. If a limit holds every account, Worker tasks pause, and messages to Workers and the Dispatcher are held; a timer runs right after the first limit resets and continues them, with a cut-off Dispatcher turn picked up again. The 2-minute check stays as a backstop. The usage tooltip shows when a held account's limit resets.
73. **Self-review before a PR.** With Settings > Models > Workers > "Self-review before PR" on (default), each code task's message tells the Worker to follow the plugin's `self-review` skill before `gh pr create`: commit, measure the diff against `origin/<default>`, have the `self-reviewer` subagent read it, fix the findings that hold up, and put a one-line result in the PR body (`Self-review: 2 fixed (…)`, `no findings`, or `skipped (small change, N lines)`). The full review stays out of the PR.
    - **Small changes skip it:** at most 30 changed lines in at most 3 files (lockfiles and generated files not counted), or docs and comments only, such as CLAUDE.md PRs (decision 28). The limits are in `src/main/agents/selfReview.ts`; per-task usage, once it exists, can show whether they are right.
    - **The reviewer** is registered on every Worker session with the SDK's `agents` option. It runs on the Dispatcher model (Sonnet 5.5 by default), like the auto-answer check, at medium effort with at most 25 turns and only Bash, Read, Grep and Glob. Its prompt keeps it read-only and asks for at most 8 one-line findings. It reads the diff itself, so the Worker spends no tokens pasting it.
    - **The rule is in the task message, not the Worker system prompt,** so switching it applies from the next task without restarting Worker sessions. Fixes for review comments and follow-ups are not self-reviewed.
74. **Spend per task.** Each task keeps what its turns cost and their tokens (input, output, cache read, cache write), shown on its result card, in the Results list (cost only, tokens on hover), in `task_detail`, and on its line in `tasks/YYYY-MM.md`.
    - **Labelled "API-equivalent estimate".** The figure is Claude Code's `total_cost_usd` at API list prices; Team and Enterprise subscriptions are not billed it. It is shown and recorded only: routing and assignment never look at it (preference of 2026-11-21).
    - **Per turn from running totals.** `total_cost_usd` and `modelUsage` are cumulative for a session (subagents such as the self-reviewer included), so `session.ts` reports the growth since the last result. The last totals are saved per session (`sessionSpend` on the Worker and the Dispatcher), because a resumed session, after a restart or an account failover, continues from its saved totals. A resumed session without saved totals (one from before this change) cannot be split into old and new turns, so its first result only sets the baseline rather than charging its whole history to the current task. A total that goes down means the counter started over and counts in full; an all-zero result (crash, startup error) is ignored. Resuming keeps the session id (the app never forks), and the app never sends `/clear`.
    - **Which task.** A Worker's turn counts toward its open task, else its latest one (a message to an idle Worker). Hidden turns (`/compact`) and turns a usage limit cut off count too.
    - **The Dispatcher is counted apart,** by month: its own sessions plus the answer-on-your-behalf check. This month's figure is at the top of the context indicator's menu.
    - `tasks/YYYY-MM.md` gets the spend at the first finish only; review fixes and follow-ups later add to the task (card, `task_detail`) but not to that line. Tasks from before this change show nothing.
75. **Failed CI goes back to the Worker; open PRs show merge readiness.** The PR monitor's `gh pr view` now also reads `statusCheckRollup`, `mergeable`, `reviewDecision` and `headRefOid`.
    - **Readiness on the task (`prChecks`).** CI is passing, failing, running or none (checks bucketed like `gh pr checks`; a re-run replaces the older check of the same name; skipped checks don't count), plus conflicts and the review decision. The result cards (chat and the Results list) and the Worker view's task list show it as badges while the PR is open; the failed check names are in the CI badge's tooltip. Unresolved review threads are not counted yet (that needs GraphQL).
    - **Same path as review comments.** A Worker idle on its open PR (`pr_open`) gets new review comments first; failed CI waits for the next check. The message starts with `[CI failure]`, lists each failed check with its link, and for GitHub Actions adds the end of `gh run view <id> --log-failed`: timestamps and color codes removed, each failed job's last lines (about 80 lines and 6,000 characters shared between jobs), at most 3 runs. Checks from other CI (commit statuses, or check runs whose link is not an Actions run) get only the link. The Worker is told not to change unrelated code for failures the branch did not cause (flaky tests, CI setup, secrets) and to say so instead.
    - **When to act.** A failure goes out once its own Actions run has finished (the failed log is readable only then); other checks still running don't hold it back. Cancelled checks and ones waiting for approval are shown as failing but not sent.
    - **No loop.** Handled failures are stored on the task (`seenCiRuns`: the Actions run ID, or the external check plus the head commit), so a run is sent once; a re-run of the same run ID is not sent again. Each task gets 3 automatic fixes (`ciFixAttempts`, `MAX_CI_FIXES` in `src/main/prchecks.ts`). After that, a new failure becomes one question in the decision inbox: "Keep fixing" gives 3 more tries with the latest failure, "I'll look at it" stops, and a typed answer goes to the Worker with the failure. The question is withdrawn if the PR is merged or closed.
    - **Usage is not checked here** (decision 72): fixes go out like review comments, and wait only if a usage limit actually holds every account.
76. **Task status follows the Worker.** A Worker running on a task never leaves that task queued, and a Worker stopped by an error never leaves it running.
    - **Any message resumes a paused task.** Before, only the limit timer (or the 2-minute check) moved a task a usage limit paused back to running. A `send_to_worker`, a user message, a review comment or a CI failure that reached the Worker first ran it on a task still marked queued, so the task showed under both Running and Queue. Now every path that reaches an open session does the same thing: the task runs again, messages held during the limit go first, and the Worker gets "continue" only when nothing else is going out. A message held because no session can open also moves the Worker's running task to the queue.
    - **Started or not (`startedAt`).** A task assigned while every account was limited gets its task message when it resumes, even on a Worker that already has a session from an earlier task. Before, such a Worker was only told to continue. Tasks saved before this count as started once their Worker has a session.
    - **A dead session fails its task.** When the Claude Code process dies or never launches, no turn result comes, so the task stayed running next to a Worker in error. Now the task fails with the error, posting the usual failure card and update to the Dispatcher. A task a usage limit paused stays queued. Telling the Worker to continue picks the failed task up again (within 3 days, like a follow-up), and its report settles it.
    - **Errors have their own sidebar section.** "Stopped with an error" lists Workers in error below Queue; they no longer sit under Running. The error is in the row's tooltip.
    - **Restart settles older state.** A Worker saved as running on a queued task continues it. A Worker saved in error has its running task failed instead of retried. Paused tasks start at once if their limit reset while the app was closed (before, they waited for the 2-minute check).
77. **Cancelling queued tasks.** A task waiting to start, queued (paused until a usage limit resets) or blocked (waiting for a merge, decision 43), can be cancelled; it then never starts on its own.
    - **Where.** An × on each row of the sidebar's Queue (shown on hover), "Cancel task" in the Worker view's task list, and "Clear" on the Queue heading for all of them. Each asks first in an in-app dialog that lists what goes, including the waiting tasks cancelled with it. The Dispatcher has `cancel_task` and `clear_queue`, so "clear the queue" in the chat works; it does not ask again, since the user asked for it.
    - **Running work is untouched.** Only `queued` and `blocked` tasks qualify, and not one whose turn is under way in its session. Anything else is refused with a hint to stop it from its Worker; Stop works as before.
    - **Waiting tasks are cancelled with it.** A task that waits (`after_task_id`) for a cancelled one could never start, so it is cancelled too, through chains of waiting tasks. This matches a PR closed without merging (decision 43). The dialog names them before anything happens and the chat lists them after.
    - **Work is never deleted.** The task branch (local, and remote if it was pushed) is deleted only when it has no commits beyond `origin/<default>` and the worktree, while on it, has no uncommitted changes (ignored files such as a copied `.env` don't count). It is read from local refs, so no fetch is needed: a Worker's push updates `origin/<branch>` in the shared repository. A branch holding work is kept and the chat says where to find it. The worktree is moved back to the default branch (detached) unless the Worker is busy in it. A Worker left with only cancelled tasks and a clean worktree is archived (decision 25), which removes the worktree; it can be restored like any archived Worker.
    - **Open PRs stay.** A task that already finished and was queued again for review comments, a CI fix or a follow-up keeps its result: only the queued work is dropped, and it goes back to "PR in review" (or "done"). The PR is not closed; the chat suggests closing it on GitHub if it is no longer needed. Its waiting tasks keep waiting for that PR. Comments and CI runs already sent stay marked as seen, so they are not sent again.
    - Messages held for the paused work (decision 72) are dropped with it. A Worker whose session had already started the task is told it was cancelled at the start of its next message, so it does not pick it up again. The Dispatcher hears about cancellations from the UI with its next message.
78. **Suggest things to remember (M1).** After the user answers a decision or corrects an auto-answer "just this once", a low-effort structured-output call on the Dispatcher model (like the auto-answer check) asks whether the exchange holds a fact worth reusing. If it does, a "Remember this?" card appears in the chat inspector with Save, Edit and Dismiss; nothing is saved without the user.
    - **Few cards:** only when the model reports high confidence and no duplicate, at most one card per task (shown cards count, including dismissed ones; a decision without a task counts on its own), and never for a bare Allow or Deny or for a correction that already fixed the preference. The fact it proposes is recalled again and dropped if one memory line already has most of its words (Korean particles stripped).

81. **Back and Forward through screens; Done today and Archived filter the Worker list.** The window keeps a screen history like a browser. A screen is the view tab plus what is open in it (`Screen` in `src/shared/history.ts`: view, selected Worker and whether its conversation is open, its Chat/Changes tab, selected repository, memory file, Worker list filter).
    - **What counts as a step.** Every user navigation goes through `go()` in the renderer: a view tab (toolbar, ⌘/Ctrl+1–4, links to a view), opening or closing a Worker's conversation (sidebar rows, the Worker list, "Send message", result and decision links), its Chat/Changes tab, picking a repository or a memory file, going to a decision, and a Worker list filter. The screen it leaves goes on the Back stack. Moving to the screen already shown adds nothing, the same screen is never stored twice in a row, and a new step clears Forward. Each side keeps 50 entries. Scrolling, selections inside the chat inspector and search text are not steps. Settings and the cancel dialog are not steps either: Back closes them first, and Forward waits until they are closed.
    - **Stale entries.** A step back to the conversation of a Worker that no longer exists is skipped; on other screens that Worker is just deselected, and so is a removed repository. A step that would then look like the current screen is skipped too.
    - **Inputs.** Mouse side buttons (`mouseup` with button 3 or 4 in the page; their default is blocked), the `browser-backward`/`browser-forward` app commands that Windows and Linux send for those buttons and for Back keys (main process → `nav` IPC), Alt+←/→ (not while typing in a field), and ⌘[ / ⌘] on macOS. One press could arrive both ways (Electron documents the app command for mouse back buttons; in a test, `WM_XBUTTONDOWN`/`UP` posted to the window reached the page only as a mouse event, while a posted `WM_APPCOMMAND` arrived as the app command), so a step from another input in the same direction within 300 ms is dropped as its echo (`NavInput`); repeats from the input that counted go through, so a fast double click still steps twice. Trackpad swipes are not handled.
    - **Done today and Archived Workers.** These sidebar rows used to switch to the Worker view, which did nothing while a conversation was open. Now each goes to the Worker list, closing the conversation, and filters it: Workers with a task finished today (done or PR open, the rule the row's count uses; the count is tasks, the list is Workers), or archived Workers. The list header shows the filter as a chip with "All" to clear it, a filter with no Workers shows an empty state, and the sidebar row is selected while that filtered list is on screen. The filter stays while a conversation is open, so closing it returns to the filtered list; "All" clears it. Back returns to the conversation that was open before.

83. **A cap on Workers running at once (B3).** Settings > Models > Workers > "Workers at once" sets how many Workers run at the same time: 3 by default, 1 to 8 (`src/shared/slots.ts`).
    - **A slot is a Worker with a running or waiting task.** A Worker waiting for an answer keeps its slot, since it goes on once answered. A Worker counts once, however many of its tasks are open, and a Worker that holds a slot may take more work (`create_task` with `worker_id`). Queued, blocked, in-review and finished tasks hold none.
    - **Every start waits for a slot.** A new task, a task whose PR was merged (decision 43), review comments and CI fixes for an open PR (decision 75), and work interrupted by a restart all start only when a slot is free. Otherwise the task is `queued` with `queueReason: 'slot'`: the Worker is assigned, but its session gets nothing yet. When a slot frees (a task finishes or fails, or a Worker goes idle), the task that has waited longest starts; a queued task's `updatedAt` is when it joined the queue. After a restart, interrupted work resumes in Worker order up to the cap; the rest wait and are told to continue when they start.
    - **Work under way is never held.** Messages and answers to a running, waiting or idle Worker go out at once, including a follow-up that reopens its finished task. A message to a Worker whose task waits for a slot is held and goes out right after the task message. A message to a Worker paused by a usage limit resumes it only when a slot is free; otherwise its task waits for one, with the message.
    - **Changing the cap.** Raising it starts waiting tasks at once. Lowering it stops nothing: running Workers finish, and new work waits until fewer run than the new cap.
    - **Two kinds of waiting.** The sidebar's Queue, task lists and the status pill say "Waiting for a slot 3/3" (slots in use / cap) or "Waiting for limit" (a usage limit, decision 72). Tasks queued before this change have no reason and count as waiting for a limit. When a limit resets, its paused tasks take free slots before tasks waiting for one, since they held a slot when they paused; any past the cap then wait for a slot. Both kinds can be cancelled (decision 77).
    - **The Dispatcher knows.** Its Worker list marks tasks waiting for a slot, `create_task` and `send_to_worker` say that the task waits and starts by itself, and its prompt tells it not to cancel or re-create such a task. The chat event reads "it starts when a Worker slot frees up (3/3 in use)".
    - The cap counts Workers, not usage: nothing is held back because of usage (decision 72 stands). A Worker with a queued task is not archived automatically (decision 25). Archived by hand, it keeps its worktree and comes back when the task starts.
84. **One PR, one entry, even when several tasks record it.** A follow-up that pushes to an open PR's branch (resolving its conflicts, say) reports the same PR URL, so the task that opened the PR and the follow-up both held it. The sidebar listed the PR under each task, the repository list counted it twice, and the PR monitor checked it per task: comments the opening task had already handled went to the follow-up again, and a merge was announced, notified and cleaned up twice. Tasks are now grouped by PR (`src/shared/prs.ts`; the same host, owner, repository and number, whatever the URL's case or trailing path).
    - **Shown once, under the task that opened it.** "PRs in review" and the repository list's PR count show one row per PR: the first task that recorded it, whose title says what the PR is. Like a single task fixing review comments, a PR that any task is working on again (running, waiting or queued) leaves the list while that work shows under Running or Queue. Each task's own result card and task list entry still link the PR.
    - **Checked once, handled by the task that opened it.** The monitor reads each PR once and keeps its readiness on every task in review on it. Review comments and failed CI go only to the task that opened it (its branch is the PR's head), and only while no task is working on the PR. It first takes over the comments and CI runs any task on the PR already handled, so a follow-up's history is never sent again; it takes over their CI fix count only while it has none of its own, so "Keep fixing" (decision 75) still resets it.
    - **Settled once.** On merge or close every task in review on the PR is finished, each distinct branch is cleaned up once, and the chat, the Worker logs, the Dispatcher update and the notification say it once, with the opening task's title. Other tasks that recorded the PR (later work that failed, for one) keep their status but take the PR's state. Tasks waiting (`after_task_id`) on any of them start, or are cancelled if the PR was closed. A task that records a PR already settled settles quietly.

86. **Every decision says why, and new work goes to the Worker that knows the code.**
    - **Why it asks.** A decision now carries a two-part reason (`src/shared/askWhy.ts`): what is asked (which Worker, which task, which action) and why the user must decide (risk or impact). The card, the sidebar row and the OS notification show the same text. Every source has one: a tool permission (the always-ask rule with its risk, a path outside the Worker's folders, Claude Code's own reason, or auto mode being unsure, followed by Claude Code's note on what approving grants), plan approval (nothing has changed yet; approving lets it change the repository and open a PR), a Worker's question (the advisor's reason for not answering, which its existing call already returns), the Dispatcher's `request_decision` (a new optional `why`), and the PR monitor's question after the CI fix cap. All of it is built from rules. The only agent-written parts are text the agents already produce: the Bash call's own description, the advisor's basis, and the Dispatcher's `why`. No extra model call is made.
    - **Who takes a new task.** `create_task` without `worker_id` reuses an idle Worker (`src/shared/routing.ts`) when one fits:
      - It runs the same model and holds no open work (running, waiting, queued, or waiting for a merge). A PR in review does not count, since comments come back on that task.
      - Its context is below 60% of the window (150K). Compaction starts at 200K between turns and 217K mid-turn, so a new task there would soon cut the context that made the Worker worth reusing.
      - For a code task, the Worker's repository is the task's. For other tasks with a repository, the Worker has worked there.
      - For a task with no repository, it shares at least two words with the Worker's past tasks.

    - **Slots are unchanged.** A reused Worker takes a slot like any other (decision 83), and tasks created in one turn go to different Workers because a Worker given one now has open work.
87. **The Dispatcher and Workers talk to each other, and Worker news starts a Dispatcher turn.** The Dispatcher asked a Worker a question with `send_to_worker` and never got the answer: the Worker's last task was merged, so its reply belonged to no task and was dropped. Worker news reached the Dispatcher only with the user's next message (decision 10), the Dispatcher could not read a Worker's conversation, and a Worker had no way to reach it. So the user had to notice the answer and ask again.
    - **Tools.** The Dispatcher gets `ask_worker` (a question; unlike instructions it reopens no task, decision 12) and `read_worker` (status, what the Worker is doing, what is unanswered between them, and the latest messages of its conversation, without disturbing it). A Worker gets `tell_dispatcher` on its `oma` server, with kind `answer`, `request` (something the Dispatcher must do or answer: what another Worker is doing, a new task for work outside its own) or `note`. The app's own Worker tools are always allowed, in plan mode too.
    - **Where an answer goes.** `tell_dispatcher` delivers at once, in the middle of a task too, and the task goes on. A Worker that answers in plain text is covered: the turn that read a question closes it, and what it said last is the answer. If a task is open and the turn that answered (with the tool or in plain text) gave no report, the Worker is told once to go on; the task is not finished by an answer. A turn that fails or says nothing reports the question as unanswered, and so does a restart, so no later text is taken for the answer. A reply to instructions when no task is open goes to the Dispatcher as an update instead of being dropped.
    - **Automatic turns.** News worth a turn (an answer, a request, a blocked or failed task, a plan-first task that stopped without a plan, a task result) starts a Dispatcher turn by itself: 3 s after the first item so several go together, after the turn in progress if there is one, and when a usage limit resets if one holds every account. The turn gets the updates and an `[Automatic turn]` note. The Dispatcher tells the user in a few sentences what the news means, acts where needed, or replies `NOOP`, which the chat does not show. Notes, replies to instructions, the user's own messages to a Worker and merges still wait for the next message. This reverses that part of decision 10.
    - **So that it stops.** An answer starts a turn only when a question is open; otherwise it is a note. In automatic turns the Dispatcher writes to one Worker at most 3 times. After 8 automatic turns in a row in which it acted (wrote to a Worker or created a task) no more start, and the chat says so; the news is kept for the next message. Turns that only report do not count, so results keep being reported while the user is away. Both counts start over when the user sends a message or answers a decision. One task's requests start at most 5 turns; later ones wait.
    - **When a task is finished.** A turn end used to finish the task whatever it said, even "my subagents are still running". Now, in this order: a plan-first task waits for its plan (decision 51); a turn without a `RESULT:` line while its subagents still run leaves the task open; a `BLOCKED: what it needs` line, or an unanswered request with no `RESULT:` line, leaves the task `waiting` with its slot (decision 83) and the status "Waiting for the Dispatcher", until the next message to the Worker from the Dispatcher or the user; anything else finishes the task as before, with or without a `RESULT:` line. Only a message sets a stopped task going again, so the Dispatcher is told when a task stops for it (for a request made earlier too) and its prompt says to always write back, also after it created a task or asked the user. After a restart such a task is not told to continue.
    - **Shown.** One event line each in the chat ("Dispatcher → W-16 question: …", "W-16 → Dispatcher: …", requests and blocked reports), the full text in the Worker's conversation, then what the Dispatcher makes of it. A Worker whose task waits for the Dispatcher stays under Running in the sidebar, since it holds a slot, labelled "Waiting for the Dispatcher" in orange (not "Waiting for you"), and its details show what it asked.
88. **Keeping Worker contexts and cost down.** Measured over 20 Worker sessions (1,178 requests, 147M input tokens, about $95 at list prices): cache writes were 41% of the cost, cache reads 30%, output 29%. Thinking was 45% of the output at xhigh effort. Shell output was 29% of what was added to contexts, and 161 of 846 commands printed whole files. Sessions resumed after more than an hour wrote their whole context to the cache again (29% of cache writes). One Worker's implementation subagents used 4.6 times the input of its own session, because it had no way to ask for new tasks (decision 87).
    - **A finished Worker is compacted from 100K** (`WORKER_IDLE_COMPACT`), not 200K: its cache is still warm then, a later resume writes a quarter as much, and follow-ups start from a small context. While a task is open the 200K rule stands (decision 79). The 250K window stays as it is: a smaller one compacts so much more often that it saves 0–2%.
    - **Standing rules in the Worker prompt**, since skills load only when asked for: find with Grep and read a range, do not print whole files or read again what was read, keep command output short, make independent tool calls together, and start no subagents for work outside the task (ask for a new task with `tell_dispatcher`).
    - **Inline command output is capped at 12,000 characters** (`bashOutputMaxChars`; Claude Code's default is 30,000). Claude Code saves the rest to a file the Worker can read in parts.
    - **Tools a Worker never uses are left out** (`Workflow`, `ScheduleWakeup`, `ReportFindings`, `ListAgents`), so their definitions are not sent with every request.
    - **Effort.** The default stays as set. The Dispatcher's prompt now says to use medium for mechanical work (conflicts, renames, small and CI fixes) and xhigh or max only for design or hard debugging (decision 45).
